The control plane and what it manages

The server manager talks to one control plane through the TUI, the admin console or the CLI. The control plane validates, reconciles and decides when a change can apply; the game runtimes and the data layer run what they are given and report back.

How a change moves

    TUI

    For hosts where a browser is unavailable or unwanted. It runs inside the control plane container or as the CLI against the loopback control API, so it opens no port of its own. One screen answers: are my worlds really up, what is switched off and why, what is waiting, and is my manifest valid.

    Admin console

    The same control API in a browser, for server managers only. It listens on loopback unless the manifest opens it, and it is a different app from the web map that players use. The settings view is the settings reference made live: every value with where it came from, its change cost, what applies it and what it affects.

    What the control plane will not do

    • Sit on the game's path. No player traffic, telemetry or command passes through it, so its failure stops changes, not play.
    • Apply part of a generation. A change applies whole or not at all.
    • Restart a game server with players online unless the server manager confirms it, knowing who it disconnects.
    • Let a world that failed to load save over the real one.
    • Start an install on a host that falls short without saying so. The host check warns in status.
    • Open the admin console beyond loopback unless the manifest says so.
    • Hold player data. Players and their records belong to the data layer.

    Ground rules behind this page: G13 Compose owns the containers, so a change to them waits for vhd apply; G15 many worlds per install; G18 the manifest format. Open: O13 default resources per world.
